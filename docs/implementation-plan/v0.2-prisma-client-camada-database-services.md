# v0.2 - Prisma client, database health e camada de services

## Objetivo

Criar a base server-side para acesso ao banco sem espalhar Prisma pela aplicacao.

Esta versao define contratos em `app/services`, implementacoes concretas em
`app/infrastructure`, uma factory central de services e um health check simples
para validar a conexao com o Postgres.

## Contexto funcional considerado

- A aplicacao tera varios dominios acessando o banco: usuarios, eventos, pedidos,
  pagamentos, tickets, check-in, outbox e idempotencia.
- Prisma nao deve ser importado diretamente em paginas, componentes, route
  handlers ou server actions.
- Services devem ser testaveis com dependencias mockadas.
- O usuario deve ter suporte a desativacao logica via campo `active`.

## Escopo desta versao

1. Reutilizar/criar helper singleton do Prisma em `app/lib/prisma`.
2. Adicionar campo `User.active` ao schema Prisma.
3. Gerar e aplicar migration para `User.active`.
4. Criar contratos iniciais de `UserService`.
5. Criar implementacao `PrismaUserService`.
6. Criar factory central em `app/services/factory.ts`.
7. Criar contrato e implementacao de health check do banco.
8. Criar rota `GET /api/health/database`.
9. Adicionar testes unitarios de services com Vitest.
10. Configurar projeto `unit` no Vitest para specs em `app/**/*.spec.ts`.

## Fora de escopo

- Autenticacao.
- Cadastro de usuario com senha.
- Verificacao de e-mail.
- Social login.
- Atualizacao de perfil.
- Services de eventos, pedidos, pagamentos ou tickets.
- Testes de integracao com banco real.
- UI para health check.

## Decisoes tecnicas

- `app/services` contem contratos, tipos de entrada/saida e a factory.
- `app/infrastructure` contem implementacoes concretas e detalhes tecnicos.
- `app/lib/prisma` contem o singleton do Prisma Client.
- A factory expoe services por getters lazy:
  - `services.users`
  - `services.health`
- Implementacoes recebem dependencias no construtor para facilitar testes.
- Testes unitarios mockam a dependencia externa, sem conectar ao Postgres real.
- `UserOutput` e um DTO da aplicacao, nao o model gerado pelo Prisma.

## Health check

Rota:

```
GET /api/health/database
```

Resposta de sucesso:

```json
{
  "status": "healthy",
  "checkedAt": "2026-06-13T00:00:00.000Z"
}
```

Resposta de falha:

```json
{
  "status": "unhealthy",
  "checkedAt": "2026-06-13T00:00:00.000Z"
}
```

Em falha, a rota retorna HTTP `503`.

## Criterios de aceite

- Prisma Client deve ser acessado pela infraestrutura, nao por paginas ou componentes.
- `services.users.findByEmail({ email })` deve consultar usuario por e-mail.
- `services.users.findById({ id })` deve consultar usuario por id.
- `services.users.deactivate({ id })` deve marcar `active` como `false`.
- `services.health.checkDatabase()` deve executar uma consulta simples no banco.
- `GET /api/health/database` deve retornar `healthy` quando o banco estiver acessivel.
- `GET /api/health/database` deve retornar `503` e `unhealthy` quando o banco falhar.
- Testes unitarios dos services devem rodar sem Postgres real.
